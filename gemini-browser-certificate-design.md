# Gemini Browser Certificate Design

## Goal

Avoid the usual first-visit trust prompt for every Gemini capsule by shipping the browser with a starter list of known certificate public keys collected by a crawler.

This design uses two separate trust sources:

1. A local browser trust store
2. A starter list generated by the crawler

These serve different purposes and should not be the same database.

## Core Idea

The browser trusts capsules based on the `SHA-256` hash of the certificate public key.

The browser does not need to store a separate trust entry for every name listed in a certificate. Trust is attached to the actual `host + port` the user connected to.

## Trust Source 1: Local Browser Trust Store

This is the browser's long-term record of certificates that are trusted for specific capsules.

There should be one record per `host + port`.

Suggested fields:

- `host`
- `port`
- `public_key_sha256`
- `first_trusted_utc`
- `last_confirmed_utc`
- `times_seen`
- `last_certificate_pem` optional

Purpose:

- This is the browser's source of truth after first trust is established.
- Once a capsule is in this store, the browser should check this store first on future visits.

## Trust Source 2: Starter List From the Crawler

This is a shipped or downloaded list of certificate information observed by the crawler.

This list is only used when the browser does not already have a local trust record for a capsule.

There should be one record per `host + port`.

Suggested fields:

- `host`
- `port`
- `public_key_sha256`
- `last_seen_utc`
- `times_seen`
- `valid_names` optional
- `not_after_utc` optional

Purpose:

- Improve the clean-install experience
- Let first-time users visit common capsules without manually accepting a certificate for each one

This starter list can be:

- bundled with the app
- downloaded as a static CSV
- refreshed occasionally, such as every few weeks

## Trust Flow

When the user visits a Gemini capsule:

1. Look up `host + port` in the local browser trust store.
2. If found, compare the current certificate public key hash to the stored hash.
3. If they match, allow the connection.
4. If there is no local entry, look up `host + port` in the starter list.
5. If found there and the current certificate public key hash matches, allow the connection and copy the entry into the local browser trust store.
6. If the capsule is found nowhere, ask the user whether to trust it.
7. If a stored key does not match the current key, show a warning and do not silently replace it.

## Why Keep The Two Stores Separate

The local browser trust store and the crawler starter list have different meanings:

- The local store represents trust decisions that the browser has adopted for this installation.
- The starter list is only bootstrap data used to avoid a poor first-run experience.

Keeping them separate makes the behavior easier to reason about:

- starter list = bootstrap trust
- local store = ongoing trust

## Record Shape

The simplest model is one record per `host + port` in both places.

Do not create separate trust rows for every alternate name listed in the certificate.

If needed, alternate valid names can be stored as metadata in a single field, such as JSON or a delimited string.

## Update Behavior

For the local trust store:

- If no entry exists, add one after trust is established.
- If the current public key hash matches the stored hash, update timestamps and counters.
- If the current public key hash does not match the stored hash, warn the user and require a trust decision.

For the starter list:

- Keep only one current record per `host + port`.
- Update it when the crawler sees the same capsule again.
- A static export format such as CSV is sufficient.

## Minimal Starter CSV Format

```csv
host,port,public_key_sha256,last_seen_utc,times_seen
example.com,1965,abc123...,2026-06-01T00:00:00Z,14
```

## Recommended Minimal Policy

- Trust is keyed by `host + port`.
- The stored value is the `SHA-256` hash of the certificate public key.
- The browser always checks the local trust store first.
- The starter list is only used if there is no local entry.
- A match from the starter list should be copied into the local trust store.
- A key mismatch should never be silently accepted.

## Summary

This design gives the browser:

- a clean first-run experience
- a simple ongoing trust model
- a small database
- clear separation between bootstrap trust and user-local trust
